💡 今日焦點一：Agentic RAG 自主糾錯檢索（從被動匹配升級為能自我反思的檢索代理）

1. 痛點剖析：傳統 Naive RAG 的三大死穴

過去一年，許多團隊將大量內部 PDF、Notion 頁面或客服 FAQ 丟進向量資料庫，搭建了基於向量相似度的 RAG 系統。然而上線後，管理者常發現 AI 表現差強人意，甚至頻繁引發客訴。其核心原因在於傳統 Naive RAG 採用「單向線性流水線」，存在三大無法克服的致命盲點：

⚠️ 盲點一：檢索失敗仍硬答（Garbage in, Garbage out）與被迫幻覺

傳統 RAG 的流程是固定的：提問 → 向量相似度搜尋 Top-K 區塊 → 拼接進 Prompt → LLM 生成。若向量資料庫檢索出來的 3~5 個文檔片段根本沒有回答提問（例如問題特殊、資料庫暫無該資料），在「請根據上述上下文回答」的 Prompt 約束下，LLM 會產生嚴重的合規焦慮，強行將不相關片段拼接湊合，產出看似專業實則完全捏造的「災難級幻覺」。

⚠️ 盲點二：查詢語意失真（Query-Chunk Mismatch）與用戶口語表達缺陷

真實使用者的提問通常極其口語化，甚至帶有錯別字或隱含假設（例如：「上週老王說的那個報帳限制到底改成怎樣了？」）。而企業規章中記載的卻是標準公文語言（「2026 年度差旅核銷與公費報銷施行細則第 4 條之費用額度上限」）。若未經過語意重寫與意圖擴展，直接將口語轉換為向量，與法規文本的語意相似度極低，直接在第一步就與正確答案擦肩而過。

⚠️ 盲點三：封閉系統盲區與缺乏外部求證能力

傳統 RAG 系統完全受限於本地靜態資料庫。當用戶提問涉及最新政策、外部競爭對手動態或跨領域名詞時，AI 只會機械式地回覆「知識庫查無相關資料」或胡扯。它無法像真人研究員一樣主動判定：「本地內部資料庫不足以作答，我需要自主啟動外部搜尋引擎（如 Google / Tavily）進行即時求證」。

2. 核心架構：CRAG（Corrective RAG）與 Self-RAG 的自我反思機制

Agentic RAG 的本質是「將 RAG 流程交由具備推理與決策能力的 AI Agent 來主導」。它不再盲目相信第一次檢索的結果，而是在流程中引入自適應評估節點與動態糾錯閉環：

  • 檢索品質評估器（Retrieval Grader）： 檢索出文檔後，不直接生成，而是由輕量級 LLM 評估器對每個 Chunk 進行打分（Relevant vs Irrelevant），自動將噪音濾除。
  • 動態查詢重寫（Query Transformation / Rewriting）： 當評估器發現檢索到的文檔大多不相關時，自動觸發重寫節點。將口語提問拆解為多角度搜尋詞，甚至生成「假設性回答文本（HyDE）」，進行二度精準檢索。
  • 外部求援回退機制（Web Search Fallback）： 若多次重寫後本地資料依然評定為「匱乏或矛盾」，系統自動切換至聯網搜尋 API（如 Tavily、Google API），抓取最新即時資料作為補充論據。
  • 真實性與有用性自評（Hallucination & Usefulness Checker）： 答案生成後，啟動雙重檢查：(1) Groundedness：回答的每個事實點是否都有檢索來源背書？(2) Relevance：回答是否精準回應了用戶原始問題？若未通過，即刻打回重新生成。

3. Step-by-step 落地步驟：用狀態機打造 Agentic RAG 流水線

在工程實踐中（如使用 LangGraph 或 LlamaIndex），我們可以透過狀態圖（StateGraph）輕鬆建構具備反思能力的 RAG 系統：

1

步驟一：建立結構化檢索打分節點（Document Relevance Grader）

設計一個執行速度極快的小型模型（如 GPT-4o-mini 或本機 Llama-3.1-8B），使用結構化輸出（Structured Output）判定文檔相關性：

from pydantic import BaseModel, Field

class GradeDocuments(BaseModel):
    # 判定檢索文檔是否與用戶提問高度相關
    binary_score: str = Field(description="文檔是否相關，僅能回答 'yes' 或 'no'")
    reasoning: str = Field(description="判定相關或不相關的 15 字簡述理由")

# 提示詞範例：
# '你是一名嚴謹的事實稽核員。請評估檢索出的文本塊是否包含回答用戶問題所需的直接事實或推論線索。'
2

步驟二：配置自適應查詢重寫器（Query Transformation）

當檢索結果被評定為無效時，呼叫重寫節點。將原本的使用者問題轉換為更容易在向量庫或搜尋引擎中命中的語意形式：

def rewrite_query(state):
    question = state["question"]
    prompt = f"""請分析以下原始問題，並將其優化為 2~3 組更具關鍵字特異性、去除口語贅字並富含專業術語的搜尋詞彙：
原始問題：{question}
請直接輸出優化後的精確搜尋查詢句。"""
    better_query = llm.invoke(prompt).content
    return {"transformed_query": better_query, "retry_count": state["retry_count"] + 1}
3

步驟三：配置 LangGraph 條件路由分支（Conditional Edges）

在工作流中定義決策轉折點，讓程式能夠依據檢索質量自動選擇下一步路徑：

def decide_to_generate(state):
    filtered_docs = state["documents"]
    retry_count = state["retry_count"]

    if not filtered_docs:
        if retry_count < 2:
            return "transform_query"  # 重寫問題再搜一次內部庫
        else:
            return "web_search"       # 超過重試上限，轉移至聯網外部搜尋
    return "generate"                 # 檢索內容品質充足，進入生成階段
4

步驟四：建立 Groundedness 忠實度安全驗收閘門

在向終端用戶輸出最終答案之前，運行「幻覺檢驗器（Hallucination Grader）」。要求模型比對生成內容與文檔來源，若判定答案中包含了檢索上下文未涵蓋的事實宣告，立刻觸發重新約束生成，達到「100% 事實可溯源」。

⚡ 今日焦點二：GraphRAG 知識圖譜增強檢索（突破向量碎片，看懂跨文檔全域關聯）

1. 痛點剖析：傳統向量檢索的「只見樹木，不見森林」

即使我們採用了最先進的向量 Embedding 與 Rerank 技術，向量檢索天生仍存在一個不可逾越的數學本質缺陷——「局部相似性偏見（Local Similarity Bias）」。這種缺陷在面對複雜的企業級分析任務時會徹底暴露：

⚠️ 致命痛點一：無法回答全域宏觀歸納問題（Global Sensemaking Queries）

試想這兩個常見的高管級管理提問：
• 「請總結過去一年所有研發會議紀錄中，最常引發跨部門摩擦的三大架構瓶頸是什麼？」
• 「這 200 份客戶訪談中，用戶最常抱怨但尚未被列入產品 Roadmap 的潛在需求是什麼？」
向量檢索在此類問題面前徹底癱瘓！因為這類問題在單一文檔中根本沒有對應的「文字段落」，它的答案分散在數百篇文檔的蛛絲馬跡中。傳統向量檢索只能隨機挑出含有「摩擦」或「需求」文字的 5 段零碎片段，導致 AI 回答片面狹隘，完全喪失宏觀戰略洞察力。

⚠️ 致命痛點二：多跳隱性因果鏈斷裂（Multi-Hop Cross-Document Reasoning）

文檔間的因果關係往往是跨篇章存在的：
• 文檔 A 記載：「供應商甲因地震產能受損，延誤了精密晶片 X 的交付。」
• 文檔 B 記載：「精密晶片 X 是伺服器機櫃 Y 的專利核心運算單元。」
• 文檔 C 記載：「伺服器機櫃 Y 未能於 Q3 上線，導致新零售專案 Z 違約受罰。」
當用戶提問：「新零售專案 Z 違約的深層源頭是否與自然災害有關？」
傳統向量檢索尋找「專案 Z」時，只會檢索到文檔 C，完全搜尋不到文檔 A（因為文檔 A 隻字未提專案 Z）。向量斷裂導致 AI 直截了當地回答「無關」，遺漏了至關重要的因果推導。

2. 核心架構：微軟 GraphRAG 實體圖譜與階層社群摘要（Community Summary）

為了解決上述痛點，微軟研究院開源了 GraphRAG（基於知識圖譜的檢索增強生成），結合近年來開源社區廣受推崇的 LightRAG，開創了一種革命性的知識組織與檢索範式：

  • 實體與關係結構化抽取（Entity & Relation Extraction）： 文檔入庫時，LLM 會通讀所有段落，主動辨識並萃取專有名詞節點（如人物、部門、專案、軟硬體、風險）以及它們之間的定向關係（如「負責」、「依賴於」、「引發」、「升級自」），並為每條邊附帶語意描述與權重。
  • 階層式 Leiden 社群發現（Hierarchical Community Detection）： 利用圖論拓撲演算法（Leiden 演算法），系統在沒有任何人工標籤的情況下，自主將圖譜中緊密連結的實體節點聚類成群（Communities）。從底層的微型技術模組社群，聚合成系統級架構社群，再聚合成全組織級戰略社群。
  • 預先生成社群宏觀摘要（Pre-computed Community Summaries）： 在任何查詢發生之前，LLM 會由下而上為每個社群生成結構化的「情報摘要報告」。這相當於為整座龐大繁複的知識庫，預先繪製好了多維度的「各層級全景導覽地圖」。
  • 雙軌混合查詢架構（Dual Search Routing）：
    • Local Search（局部聚焦查詢）： 針對微觀具體問題（如「張工程師參與了哪些專案？」），從實體節點出發，沿圖譜鄰近邊界擴展細節；
    • Global Search（全域宏觀查詢）： 針對全局綜觀問題（如「全公司有哪些潛在技術債？」），直接調用預先生成的各級社群摘要，採用 Map-Reduce 方式平行匯總，瞬間產出宏觀洞察。

3. Step-by-step 落地步驟：企業如何低成本導入 GraphRAG

過去建構圖譜需要昂貴的標註人力，現在藉由現代大模型與輕量化開源工具，中小團隊也能在 1 天內完成部署：

1

步驟一：精準設計實體抽取提示詞（Extraction Schema）

避免讓 LLM 隨意抓取實體造成圖譜膨脹。在 Prompt 中明確限定業務相關的實體類型（例如：[實體類型]：組織、技術、專案、人員、風險、法規），並強制輸出結構化 JSON，記錄關聯強度（1~10）與具體佐證引用句。

2

步驟二：選擇合適的落地工具框架（LightRAG vs 原生 GraphRAG）

若為超大規模跨年度文檔且預算充足，可採用微軟官方 microsoft/graphrag；若重視成本、構建速度與增量更新（Incremental Update），強烈推薦開源的 LightRAG。LightRAG 將圖譜抽取與低階、高階檢索高度精簡，Token 消耗僅為原生方案的 15~20%，非常適合快速原型驗證。

# LightRAG 極速初始化範例
from lightrag import LightRAG, QueryParam
from lightrag.llm import gpt_4o_mini_complete

rag = LightRAG(
    working_dir="./my_enterprise_graph",
    llm_model_func=gpt_4o_mini_complete
)

# 批次索引文檔
with open("annual_reports.txt", "r") as f:
    rag.insert(f.read())

# 全局宏觀查詢
print(rag.query("過去三年所有產品線最核心的跨部門技術瓶頸是什麼？", param=QueryParam(mode="global")))
3

步驟三：建構智慧查詢意圖路由器（Intent Router）

設計一個前置分類節點，自動判斷用戶問題是「微觀細節」還是「全域宏觀」：
• 若提問包含「有哪些、整體趨勢、主要主題、總結全貌」等聚合意向詞，自動路由至 Global Search；
• 若提問針對特定專案編號、某人名或具體參數，自動路由至 Local Search，節省查詢成本並大幅縮減回應時間。

4

步驟四：落地成本控制四法寶

① 離線抽取模型降級： 實體抽取屬於格式化任務，使用本地開源模型（如 Qwen2.5-14B、DeepSeek-V2.5）或 Batch API 執行，可降低 80% 以上成本；
② 社群聚類深度剪枝： 限制 Leiden 演算法的聚類層級在 2~3 層，避免過度細碎；
③ 實體消歧（Entity Disambiguation）： 引入同義詞合併表（如「張總」、「張處長」與「政峰」合併為同一節點）；
④ 向量＋圖譜雙重混合（Hybrid Graph-Vector）： 向量專精局部文字相似，圖譜專精因果拓撲，兩者融合達到 1+1 > 2 的檢索天花板。
