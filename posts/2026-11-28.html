今日實戰主題一：別再背 AI 公關稿！打造附帶「情緒計分板」的 AI 高壓沙盤陪練室

為什麼直接叫 AI「幫我寫談判話術／面試回答」上戰場常失靈？

面對漲價溝通、客訴安撫、向主管提案或求職面試時，大多數人會問 AI：「如果客戶嫌太貴，我該怎麼回覆？」AI 通常會給你一段禮貌又完美的「標準公關稿」。但真實對話不是背書——對方可能有預算死線、對某個細節心存懷疑，甚至會突然反問一個尖銳問題。如果你沒有練過「臨場接招」，死背話術反而顯得生硬、更難建立信任。

高階實戰者會把 AI 改造成「動態狀態追蹤沙盤模擬器（State-Tracked Adversarial Role-Play）」：先幫對手設定不對你公開的隱藏底線與地雷，要求 AI 每回合只吐出一句真實反應，並同步顯示「信任度／耐心值儀表板」；等 5 輪攻防結束後，再一鍵喚醒「旁觀複盤教練」做逐句診斷！

💡 一句話痛點破解： 練習時「禁止 AI 一邊演對手一邊誇獎你或給建議」！先讓它徹底化身有立場、會翻臉的真實利害關係人跟你打完 5 回合，結束後再切換角色複盤，臨場抗壓能力才會真正提升。

Step-by-step 四步驟架設你的個人 AI 沙盤陪練室

  • 1
    第一步：填寫「對手心智模型（Mental Model）與難度係數」： 告訴 AI 對手的職位、KPI 壓力與「絕不輕易讓步的 2 條隱藏顧慮」（例如：財務長最怕現金流卡死、採購最在意售後風險）。把難度設為 Hard（高疑慮、不吃空泛客套話），逼自己只講對方在乎的證據與利益。
  • 2
    第二步：掛載「動態狀態計分板（State Tracker）」： 規定 AI 每次回覆最上方必須用固定格式印出數值，例如 [信任度: 45/100 | 防禦心: 70/100 | 剩餘耐心: 4/5 輪]。當你只顧著推銷自己產品、沒回答對方痛點時，信任度直接扣分；只有擊中核心疑慮時才加分。這個簡單機制能瞬間讓 AI 保持角色一致性，不會忘記自己正在生氣或懷疑！
  • 3
    第三步：下達「嚴禁出戲禁令（No Meta-Coaching Mid-Game）」： 明確寫死規則：「在收到指令 /debrief 之前，嚴禁跳出來給建議、嚴禁稱讚我的回答、每次最多輸出 120 字的真實口語反問」。這能確保你像在真實會議室一樣專注思考下一句怎麼接。
  • 4
    第四步：輸入 /debrief 啟動「雙軌複盤手術刀」： 演練結束後，要求 AI 切換成頂級談判教練，回頭檢視整段紀錄：指出「哪一輪因為哪個用詞導致信任度驟降」、揭露原本設定的隱藏底線是什麼，並把你講得不夠精準的那 2 句話重寫成可直接上場的版本。

今日實戰主題二：別再讓 AI 當橡皮圖章！AI 雙遍對抗式程式碼審查（Two-Pass Adversarial Review）

為什麼問 AI「這段程式碼有沒有問題？」總是只得到客套稱讚？

現在不論是工程師還是用 AI 寫自動化腳本的工作者，做完功能後常習慣把整段程式丟給 AI 說：「幫我檢查有沒有 Bug。」但你一定看過這種回覆：「整體架構非常清晰、命名也很規範！唯一的小建議是可以多加幾行註解……」——然後隔天跑真實資料就因為一個空陣列、漏掉 Timeout 或時區轉換當場炸掉。

這種現象叫做「橡皮圖章審查（Rubber-Stamp Review）」：當你沒有切分任務視角時，AI 為了保持禮貌與高概括性，注意力會被「讚美正常路徑（Happy Path）」吸走。真正工程級的解法叫做「雙遍對抗式審查（Two-Pass Adversarial Code Review）」：縮小餵料範圍到 Diff 變更區，並強迫 AI 分兩趟扮演完全不同的「挑刺角色」，只准找問題、不准寫好評！

💡 一句話痛點破解： 審查程式碼不要一次問「好不好」，而要拆成「Pass 1 專找崩潰反例的極端 QA ➔ Pass 2 專找漏網資安與超時的 SRE ➔ 只列 P0/P1 實質風險」，抓蟲率直接翻倍！

審查方式 關注焦點 常見漏網之魚 實戰信噪比
傳統 Linter / 語法檢查
（ESLint / Ruff）		 縮排、未用變數、型別錯誤 看不懂商業邏輯錯誤、競態條件與權限繞過 高（零幻覺，負責第一道基本衛生）

（「幫我看這段 code 好不好」）		 大架構感想、風格微調建議 對「看起來寫得很漂亮但邏輯有洞」的 AI 產出容易放水 低（廢話多、真正致命 Bug 常被漏看）
雙遍對抗式審查
（Two-Pass Adversarial）		 Pass 1 極端反例 ＋ Pass 2 資安韌性 需人工確認是否誤報（False Positive） 極高（強制要求「附具體觸發輸入」才算發現）

Step-by-step 四步驟建立你的自動化「抓蟲防線」

  • 1
    第一步：先把「機械衛生」交給確定性工具（Linter），別浪費 AI 腦力： 在讓 AI 審查之前，先跑過一次內建格式化與語法檢查（如 Python 的 ruff、JS 的 eslint / tsc）。並且在 Prompt 中明確禁止 AI 評論變數命名風格或註解多寡，讓它的全部注意力都鎖定在「會讓系統出事的地方」。
  • 2
    第二步：精準投餵「Diff ＋ 邊界契約」，而非整坨貼上： 只貼入這次新增或修改的程式碼區塊（或直接執行 git diff），並附上一行「這段程式接收什麼格式輸入、預期吐出什麼結果」。縮小上下文能大幅減少 AI 的注意力渙散。
  • 3
    第三步：強制「構造可復現的反例輸入（Concrete Counterexample）」： 要求 Pass 1 不能只說「這裡可能有空值問題」，而必須寫出：「當輸入為 items = [] 且 discount = null 時，第 18 行會拋出 TypeError 導致整批中斷」。拿不出具體反例的空泛猜測一律不准列入報告！
  • 4
    第四步：用「四項必查資安／韌性清單」執行 Pass 2 掃描： 無論你是寫大型網站還是 100 行的資料整理腳本，第二遍固定掃描這 4 個新手與 AI 最常犯的地雷：
    • 硬編碼機密： API Key、密碼或個人網址是否不小心寫死在程式裡？
    • 外部呼叫無保護： 呼叫 API 或爬蟲時，有沒有設 timeout 與失敗重試上限？
    • 資料毀損與冪等性： 腳本跑到一半中斷重跑，會不會重複寫入兩筆相同資料或覆蓋舊檔？
    • 輸入消毒： 使用者輸入或外部檔案名稱是否直接拼進 SQL 或 Shell 指令裡？
📌 進階小秘訣：用「換一隻模型互相挑刺（Cross-Model Review）」效果更驚人！
同一套模型剛寫出來的程式碼，自己審自己有時還是會有 blind spot（盲區慣性）。實戰中最有效的做法是：用模型 A（例如 Claude / Cursor）寫完功能後，把 git diff 丟給另一個模型 B（例如 Gemini / Codex）用「雙遍對抗式審查模板」抓蟲，往往能抓出原模型完全沒意識到的隱形假設！
